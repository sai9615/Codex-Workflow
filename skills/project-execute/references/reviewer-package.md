# Compact reviewer context package

The coordinator prepares one small entry point for each independent review. Keep it in the project's existing evidence location outside the distributed workflow package; link authoritative records and raw artifacts instead of copying histories or entire source trees. Compactness is a navigation aid, never a limit on review depth or required evidence. A developer summary is a claim to verify, not a substitute for the actual candidate.

## Package contents

Use this checklist as the entry-point template. Every field needs a value, an artifact pointer, or an explicit unknown/missing item with its effect on review.

| Field | Required content |
| --- | --- |
| Task and authority | Task/attempt ID; exact authorized objective and exclusions; canonical tracker, approved task revision and applicable instruction pointers; all user requirements and stable acceptance criteria, including later corrections. Map each criterion to implementation and verification evidence. |
| Baseline and candidate | Repository/checkout, base commit and candidate commit when committed. For uncommitted work, say so: record HEAD, tracked changes, untracked additions/deletions, file hashes and a manifest/diff hash identifying the reviewed state. Include protected/unrelated dirty work and how it is distinguished from this task. Never invent a candidate commit or rely on HEAD alone for dirty work. |
| Actual change | Reproducible base-to-candidate diff and changed-file inventory, including additions, deletions, renames and relevant untracked files. Describe how to verify the inventory against the working tree or snapshot. Summaries do not replace the diff; ordinary Git diff alone omits untracked additions. |
| Dependencies and architecture | Relevant callers, contracts, shared dependencies, trust boundaries and essential architecture, with source pointers. Identify affected downstream behavior and the reason for the chosen scope; link deeper context rather than preloading it. |
| Raw validation | Commands, working directory, runtime/environment, start/end times, exits, full logs and assertions/results, linked to the exact candidate identity. Distinguish targeted/full-suite, static/offline/live checks, warnings, failures, skips, not-run criteria and correction attempts. Preserve original logs; a passing summary is insufficient. |
| Risks and findings | Known risks, unresolved findings, prior findings and dispositions where applicable, assumptions and evidence gaps. Separate observed facts from developer claims. Include approval, acceptance and publication gates still open. |
| Access and recovery | Package entry-point location, authorized source/evidence roots and read-only review scope; excluded secrets, private histories, other roles' transcripts and unrelated projects. Identify who can supply missing evidence and where findings/checkpoints belong. |
| Measurement | Actor/session/role, fresh/reused rationale, requested/observed settings, timestamps, observable reads/repeated reads, defects found and native usage counters or explicit unknowns. Link the benchmark protocol for any comparison; bytes, reads and agent counts are not token or subscription savings. |

## Reviewer procedure

1. Start at this entry point. Check authority, criteria, applicable instructions, baseline/candidate identity and evidence freshness before relying on results. Independently compare the actual candidate and changed-file inventory with the supplied diff/manifest; validate relevant untracked files and deletions as well as tracked changes. Record the verified identity and any mismatch.
2. Inspect requirements, changed code and raw validation evidence independently. Follow dependencies, callers, contracts, architecture and surrounding source whenever needed for correctness, security or regression risk. The package is not a source allowlist. Further inspection remains available throughout the authorized project scope; request broader authority through main when necessary. Do not read unrelated histories or other roles' transcripts to reconstruct the task.
3. Check that commands and artifacts establish the claimed criteria for this exact candidate, with appropriate independence. Old logs are historical evidence unless their provenance establishes applicability. A changed candidate or relevant instruction/requirement drift invalidates affected evidence: identify the needed fresh checks and review before a verdict. Time proximity alone does not establish freshness.
4. Report findings with severity, criterion and source/evidence pointers; separate verified, unverified and not-run items. If essential evidence, access, identity or scope is missing/stale/conflicting, report insufficient evidence for the affected conclusion, identify the smallest missing artifact/check and return it to main. Continue useful authorized inspection, but never convert a gap to PASS or fabricate an identity/result. Main resolves authority questions; the reviewer cannot grant permission.
5. Return a concise verdict bound to the inspected identity, evidence coverage, remaining risks and actual measurement/unknowns. Preserve findings and raw evidence in the existing project records. Passing tests and a reviewer verdict do not grant user acceptance, adoption or publication authority.

The reviewer must remain independent of implementation. Read-only role instructions do not enforce filesystem isolation; report actual runtime access limits honestly. Do not weaken required tests, separate-role verification or further source inspection to make the package smaller. For reporting and accounting, use the [task report](task-report.md) and [benchmark protocol](efficiency-validation.md).

## Correction and rereview loop

Use this within the existing coordinator/developer/reviewer loop; do not add an orchestration service or another approval stage. In-scope corrections proceed under existing task authority. Main escalates material scope, design, trust-boundary, dependency or resource changes; acceptance and publication remain separate gates.

1. The independent reviewer reports each actionable finding with a stable ID, severity, location, impact, supporting evidence and required correction or acceptance condition. Main returns those findings to the same suitable developer after checking current scope, role history, candidate, context and settings. Reuse a session only while compatible; never substitute an implementer for independent review. If freshness or capacity requires another session, preserve the checkpoint and explain the change. Reuse is not presumed cheaper.
2. The developer corrects within scope, records each finding's disposition and rationale, and reruns affected validation on the changed candidate. Include relevant regression checks and broaden validation for affected dependencies or risk; never drop required checks merely because the edit is small. Preserve prior failures, findings and original logs, including unresolved or disputed findings. A developer's resolved claim is not reviewer acceptance.
3. Main supplies the same suitable independent reviewer a correction package using the contents checklist above. Add prior finding IDs/dispositions, the previous-reviewed and corrected candidate identities (honest hash manifests for uncommitted states), the exact previous-reviewed-to-corrected diff and changed-file inventory, full current inventory/identity checks against the task baseline, updated raw validation with freshness/provenance, affected criteria/dependencies and remaining risks. Preserve a reproducible previous-reviewed snapshot or equivalent artifact so the correction diff can be independently checked. Inventory all tracked/untracked changes and deletions; do not conceal unrelated or unexpected drift behind a narrow correction diff. Link prior review evidence rather than copying entire histories.
4. The reviewer verifies both identities, the correction diff, full inventory drift and updated evidence before relying on the previous review. Begin with prior findings, their corrections and regression paths. Inspect source and raw evidence independently; no developer disposition or previous verdict replaces inspection. Expand to callers, contracts, shared dependencies, architecture or the full relevant scope when dependency impact, risk, unexpected changes, incomplete provenance, stale context or possible anchoring/contamination warrants it. Ask main for missing scope/evidence, or a fresh independent reviewer when necessary. Delta-first describes the starting point, never a limit on inspection or a reason to carry forward stale conclusions.
5. The reviewer marks each finding resolved, unresolved or superseded with evidence and records new findings, regressions, inspected scope and remaining gaps. Bind the verdict to the corrected identity and current criteria. Return actionable findings through the same loop until required validation and independent review support the task outcome; missing essential evidence stays insufficient evidence. Material changes follow main's existing approval rules. Record every pass/correction and actual time, reads and counters or unknowns; neither reuse nor a smaller delta establishes efficiency savings.
